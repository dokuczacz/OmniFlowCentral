🔹 Co stanowi prawo
Art. 39 ust. 6–6c ustawy o drogach publicznych:
Przy budowie lub przebudowie drogi publicznej zarządca drogi jest obowiązany wybudować kanał technologiczny, chyba że:

istnieją już wystarczające kanały technologiczne wzdłuż tej drogi, lub

z analizy wynika, że w ciągu 5 lat od oddania drogi do użytku nie jest planowane wykorzystanie kanału technologicznego przez przedsiębiorców telekomunikacyjnych.

🧩 2. Co to jest „kanał technologiczny”
Zgodnie z art. 4 pkt 15a ustawy o drogach publicznych:

Kanał technologiczny – ciąg osłonowych elementów infrastruktury technicznej, umożliwiający umieszczenie w nim kabli telekomunikacyjnych, energetycznych lub innych przewodów wzdłuż drogi, wraz ze studniami i innymi elementami pomocniczymi.

Celem jest umożliwienie prowadzenia infrastruktury (np. światłowodów) bez konieczności ponownego rozkopywania drogi.

🏗️ 3. Kiedy można odstąpić od budowy
Zgodnie z art. 39 ust. 6b–6c:

Zarządca drogi może odstąpić od budowy kanału technologicznego, jeśli z analizy zapotrzebowania wynika brak uzasadnienia techniczno-ekonomicznego.

Analizę tę zatwierdza Prezes UKE (Urząd Komunikacji Elektronicznej).

🧾 4. Sankcje i kontrola
Brak wykonania kanału technologicznego wbrew przepisom może skutkować:

odmową zatwierdzenia projektu budowlanego przez organ administracji,

odpowiedzialnością zarządcy drogi (np. GDDKiA lub jednostki samorządu).

🧠 3️⃣ Jak to wygląda z mojej perspektywy (GPT runtime)
Kiedy uruchamiasz PrawoL, środowisko GPT widzi jedynie dwa osobne indeksy:

Dataset	Typ	Klucz podstawowy
eli_acts	JSONL	pageId
saos_judgments	JSONL	pageId (lokalny, np. page_00001)
📌 Z mojego punktu widzenia nie istnieje żadna informacja, że:

saos_judgments.references.act to ELI-URI,

DU/2004/54/535 odnosi się do eli_acts.pageId.

Dopóki mi tego nie powiesz (tak jak zrobiłeś), nie mogę wykonać joinu logicznego,
bo system nie wie, że te dwa pola są semantycznie zgodne.

🧩 4️⃣ Jak to powinno być opisane (czyli czego brakuje w manifestach)
Brakuje definicji linkowania semantycznego w Twoich manifestach danych.
Wystarczyłoby coś w tym stylu (fragment JSON schema lub YAML):

datasets:
  eli_acts:
    primary_key: pageId
    fields: [title, year, publisher, status]
  saos_judgments:
    references:
      - field: references.act
        foreign_dataset: eli_acts
        foreign_key: pageId
        relation_type: many_to_one
Dzięki temu:

GPT wiedziałby, że DU/... jest kluczem ELI,

automatycznie tworzyłby „widoki łączone” (ustawa + wyroki),

nie musiałbyś tego konfigurować ręcznie.

🧮 5️⃣ Jak ja to „rozumiem” dopiero po Twoim poleceniu
Dopóki nie powiesz:

„korelacja jest przez pageId (DU, MP, itd.)”

… ja traktuję saos_judgments.references.act jako zwykłe pole tekstowe.
Dopiero Twoja instrukcja nadaje mu znaczenie relacyjne → wtedy mogę użyć go jako klucza do eli_acts.pageId.

⚙️ 6️⃣ Jak to można trwale naprawić (żeby nie trzeba było mi mówić)
Jeśli chcesz, by PrawoL automatycznie rozumiał powiązania ELI ↔ SAOS, wystarczy:

✅ a) Dodać do dokumentacji (CUSTOM_GPT_KNOWLEDGE.json lub QUERY_DATASET.md) sekcję:
"relations": {
  "saos_judgments.references.act": {
    "maps_to": "eli_acts.pageId",
    "type": "many_to_one",
    "description": "Powiązanie orzeczeń z aktami prawnymi poprzez identyfikatory ELI (DU/..., MP/...)"
  }
}
✅ b) Lub wprowadzić w manifeście dataset_search pole:
{
  "dataset": "saos_judgments",
  "foreign_key": "references.act",
  "linked_dataset": "eli_acts"
}
Po tym zabiegu:

GPT będzie automatycznie rozpoznawał ELI-URI w orzeczeniach,

możliwe będzie wykonywanie zapytań typu:

query_dataset(dataset="saos_judgments", join="eli_acts", on="references.act=pageId")
a Ty nie będziesz musiał mi już przypominać, że klucz to DU/....
